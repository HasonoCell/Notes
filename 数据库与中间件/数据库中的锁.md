
理解锁的关键在于分清维度。任何一个具体的锁操作，都是以下三个维度的组合：

- **策略维度（思想层）**：乐观锁 vs 悲观锁（处理冲突的指导思想）
- **粒度维度（资源层）**：表级锁 vs 行级锁 vs 应用资源锁（锁定的范围）
- **模式维度（权限层）**：共享锁（读锁） vs 排他锁（写锁）（锁的访问权限）


# 乐观锁与悲观锁

| 类型 | 核心思想 | 实现方式 | 适用场景 |
| :--- | :--- | :--- | :--- |
| 乐观锁 | 假设冲突极少，不上锁，提交时检查 | 版本号（Version）、时间戳或状态字段 | 读多写少，并发冲突低的场景 |
| 悲观锁 | 假设冲突频繁，先获取锁再操作 | 数据库提供的排他锁（如 `FOR UPDATE`） | 写多读少，对数据一致性要求极高的场景 |

# 表级锁与行级锁

| 类型      | 描述                      | 并发性能 | 典型语法                    |
| :------ | :---------------------- | :--- | :---------------------- |
| 表级锁     | 锁定整张表，开销小，加锁快，但冲突概率大    | 低    | `LOCK TABLE ...`        |
| 行级锁     | 锁定具体的数据行，开销大，加锁慢，但冲突概率小 | 高    | `SELECT ... FOR UPDATE` |
| 页级锁（补充） | 介于表锁和行锁之间，锁定数据页（极少使用）   | 中    | 数据库自动管理                 |

# 共享锁与排他锁

这是描述锁“权限”的属性，可以附加在表级锁或行级锁之上。

| 模式 | 别名 | 加锁者权限 | 对其他事务的影响 | 兼容性 |
| :--- | :--- | :--- | :--- | :--- |
| 共享锁 | S 锁（读锁） | 只能读，不能写 | 允许其他事务加共享锁读，但阻止任何修改 | 共享锁与共享锁兼容 |
| 排他锁 | X 锁（写锁） | 可读可写 | 阻止其他事务任何形式的访问（读写均阻塞） | 排他锁与任何锁均冲突 |


# 特殊锁机制详解

## 建议锁（Advisory Lock）

建议锁似乎是 PG 特有的锁。
- **所属层级**：应用层与数据库中间件之间的高级特性，属于自定义资源锁。
- **核心特征**：协作式、非强制。数据库仅记录锁状态，不强制执行拦截。
- **策略归属**：属于悲观锁的一种特殊实现形式。
- **典型用途**：分布式定时任务防重跑、应用层互斥（Mutex）、自定义业务资源协调。
- **重要区分**：建议锁锁定的不是数据库表中的行，而是一个由应用自定义的 ID（例如订单号或用户ID）。

## 意向锁（Intention Lock）

- **所属层级**：数据库内核级别的自动辅助机制。
- **核心作用**：用于提升表级锁与行级锁之间的检测效率。当事务准备锁住某些行时，数据库会自动在表级别添加一个“意向锁”，相当于在表门口挂一个“里面有行被锁”的提示牌，便于其他事务申请表锁时快速判断。
- **分类**：意向共享锁（IS）和意向排他锁（IX）。

## 间隙锁（Gap Lock）

- **所属层级**：行级锁的变种，归属于 InnoDB 引擎的事务隔离级别实现。
- **核心作用**：锁定索引记录之间的“间隙”，防止其他事务在间隙中插入新数据。
- **存在意义**：专门用于解决可重复读（Repeatable Read）隔离级别下的幻读问题。


# SQL 命令速查表（PostgreSQL）

| 操作目标       | PostgreSQL 语法                       | 锁的维度组合        |
| :--------- | :---------------------------------- | :------------ |
| 锁住特定行（排他）  | `SELECT ... FOR UPDATE;`            | 悲观 + 行级 + 排他  |
| 锁住特定行（共享）  | `SELECT ... FOR SHARE;`             | 悲观 + 行级 + 共享  |
| 手动锁整表（禁止写） | `LOCK TABLE ... IN EXCLUSIVE MODE;` | 悲观 + 表级 + 排他  |
| 手动锁整表（禁止改） | `LOCK TABLE ... IN SHARE MODE;`     | 悲观 + 表级 + 共享  |
| 建议锁（排他）    | `pg_advisory_lock(id);`             | 悲观 + 应用级 + 排他 |
| 建议锁（共享）    | `pg_advisory_lock_shared(id);`      | 悲观 + 应用级 + 共享 |

# 实战组合解析

在日常开发中，遇到的锁均是上述维度的组合体：

- `SELECT * FROM orders WHERE id = 1 FOR UPDATE;`
  - 解析：悲观锁 + 行级粒度 + 排他模式。
  - 行为：锁住订单 ID 为 1 的这一行，其他事务无法修改或查询该行（取决于隔离级别）。

- `LOCK TABLE users IN ACCESS EXCLUSIVE MODE;` (PostgreSQL)
  - 解析：悲观锁 + 表级粒度 + 排他模式。
  - 行为：完全锁死 users 表，所有读写操作全部阻塞，用于 DDL 或数据迁移。

- 数据库自动添加的意向排他锁（IX）
  - 解析：悲观锁 + 表级粒度（逻辑标识） + 意向模式。
  - 行为：开发者不可见，由数据库内核在执行 `FOR UPDATE` 时自动附带，用于表级锁与行级锁的冲突仲裁。
